# Epic 8 decisions

What the PRD, the addendum and the code leave open or state twice for v0.8, settled while writing the Epic 8 stories on 2026-10-28 under the owner's delegation of design decisions, then reworked the same day after a review of the stories (P-74): every finding accepted, the existing decisions amended in place with the finding they answer (`review Fn`), and new rules added from D-426. Numbering continues the earlier files: principles from P-70, decisions from D-400 (D-343 to D-399 are left to Epic 7's rework), so a `P-n` or `D-n` is unique across epics and Epic 8 stories cite all seven files. Stories cite these decisions and name the test that proves each one; this file states the rule, never the test data. A later change edits this file with the fact that motivates it, like the architecture.

"The addendum" is `docs/architecture-v0.8.md`. "Story 2.8" is that story as D-170 amends it (ACs 18 to 21): v0.8 starts from it and rebuilds none of it. "Story 2.13" is the v0.2 story D-172 created from this review: catalogue notices for values a program reads, and approval lines that name their action. A gate's research notes entry is named by its gate ("the gate 1 entry") until D-401 gives it a number. Two `RunPlan` types appear here and are always named by module: `relay::run::RunPlan` (an action's run) and `workshop::vector::RunPlan` (a workshop run's plan) (review F28).

  - `Admission::ResolveThen` carries a list, one `(write, targets action, params)` per write with a targets action; each is resolved and judged, and any `out` refuses `order_required`;
  - a relay action whose program's last path segment is `ansible-playbook` and that no write names as its check gets a story 2.13 notice kind `unscoped_check_mode_read` ("a check-mode read judged on its parameter rules only"), and its projects join the check-mode scan;
  - `dry_run_for_workers` (8.4) marks an action listed in some template's `relay_actions` that is the check of any write of the catalogue, or such an unscoped check-mode read.

  This departs from AD-158 step 9's "the check of at least one write the project lists" (P-71). (8.3, 8.4, 8.10, 8.11, 8.15)
- **D-428.** A target value is a name, never an Ansible pattern (review F3). `judge` refuses, first among the target rules (after `target_undeclared`, before `targets`), a target value failing `scope::is_host_name` or equal, ignoring ASCII case, to an entry of core `scope::ANSIBLE_RESERVED_PATTERNS` (seeded `all`, `ungrouped`, `localhost`; from then on the list), with `OutOfScopeCause::TargetNotAName`. Vector cases use a permissive scope pattern: values carrying `:`, `,`, `&`, `!`, `*`, a leading `~` or `@`, and every reserved entry (derived by iterating the constant), each `out`. With an unparsed listing (D-403) this rule carries the whole scope. The README says the scope rule matches names, never patterns. This departs from AD-154 6a's order (P-71). (8.5, 8.6, 8.10, 8.12)
- **D-429.** Mailbox lines in the limiter, replays and connections (review F4, F17, F31):
  - `WorkerRefusal` gains `not_utf8` and `read_deadline`; `admit` takes every `MailboxLine`, and a mailbox `refused` line (`oversized`, `not_utf8`, `read_deadline`) maps to its refusal at step 1, after which it counts as a request line for `too_soon`, `run_cap` and abuse, and is answered and journaled like any refusal, so twenty bad connections end the run;
  - the limiter keeps the highest `seq` seen (folded from `worker_relay` lines); a `request` line at or below it is dropped, counted in a diagnostic and never run, whatever `docker attach` replays after a re-attach;
  - `admit` returns the limiter's next state, so the fold from lines and the live state compare like with like; `busy` starts at admission, is never folded, and a restart clears it;
  - the mailbox serves at most `MAILBOX_MAX_CONNECTIONS` at once, well under its 32-process limit; a connection past it is closed unread.

- **D-430.** Run ids are unique per process (review F12). Every run host `relay::run` starts takes the id `{now_ms:x}-{pid:x}-{n:x}`, `n` a per-process counter, so a targets run and its write inside one `officina run`, and up to `max_workers` `workshop-relay` threads of one window, never share an id that `satisfying_check`'s set of succeeded runs or a kept output's name would confuse. - **D-431.** Relative deadlines for the mailbox (review F15; D-242's rule, D-209 being withdrawn). `officina-entry mailbox --deadline-s <s>` counts from its own start; `MailboxLine::Started` carries the port, never a clock; the `ack` carries a remaining duration in milliseconds (D-418), never a value of the window's clock; no skew is recorded from mailbox lines. - **D-432.** The client paces itself (review F20).
